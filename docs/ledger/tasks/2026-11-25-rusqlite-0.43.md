# rusqlite 0.32 → 0.43 (bundled SQLite 3.54)

## Objective

Clear RUSTSEC-2026-0459 (CVE-2026-119375, CVSS 4.0 6.8): bundled SQLite before
3.54.0 can return uninitialized page-cache memory. The patched bundle is
`libsqlite3-sys` ≥ 0.39, which needs `rusqlite` ≥ 0.41.

If this is mechanical and green today, it goes into 0.12.1. If it drags (API
churn, changed behaviour), 0.12.1 ships without it, and its notes state the
advisory and its reachability (owner, 2026-11-25).

## Reachability of CVE-2026-119375

**What the bug needs** (advisory text): a process opens a database file
*together with a sibling `-wal` file whose page size differs*. A crafted pair
makes ordinary queries return stale bytes from the process's memory. The vector
is local: someone has to be able to write those two files where the victim opens
them. SQL text does not trigger it, and neither do bound values.

**How Kulyrax uses SQLite:**
- The SQLite adapter opens one file, the `path` in the operator's config
  (`sql/sqlite.rs`, `Connection::open(path)`), and sets `journal_mode = WAL`.
  So the `-wal` path the bug needs is in use.
- Every statement is Kulyrax's own; event values are bound parameters. Rebuilds
  use shadow tables in the same file.
- No `ATTACH`, no extension loading, and no other database file is ever opened.
- Event data never names a file Kulyrax opens as a database.

**So:** an attacker needs write access to the directory of the configured database,
to swap in a crafted `app.db` plus `app.db-wal`. Anyone with that access can
already rewrite the projection and its guard table directly, a stronger
capability than reading stale memory. Sending events (gRPC, a watched
directory, an outbox table) gives no path to it. **Reachability: low.** Exposed
only where the database file lives somewhere a less trusted party can write.

The examples' `dbtool`s open only databases they create themselves; same
conclusion.
