# Kulyrax v0.8.0

## Status

Alpha — feature release covering **Phases 22–25**: every storage kind now has a real
database backend (Redis, MongoDB, Neo4j, MySQL), and the four backend traits behind
them are a public, documented extension point for community connectors.

---

## Highlights

### Redis key-value backend (Phase 22)
- `AdapterConfig::Redis` — a second key-value backend alongside the file adapter,
  behind the new `KvBackend` seam (`adapter/keyvalue/exec.rs`), reusing `KvGuard`
  unchanged as the wire format.
- Atomic guard-and-value writes via `WATCH` / `MULTI` / `EXEC` with a bounded 5-attempt
  retry on conflict (`redis::transaction()`'s own helper retries unboundedly, so this is
  a hand-rolled loop, not the crate default).
- `RedisAdapter` declares `write` / `upsert` / `delete` — deliberately **not**
  `transactions`: WATCH/MULTI/EXEC is optimistic concurrency, not a lock, and the
  capability vocabulary now says so explicitly.

### MongoDB document backend (Phase 23)
- `AdapterConfig::MongoDb` — a second document backend alongside the file adapter,
  behind the new `DocumentBackend` seam, reusing `ProjectionGuard` unchanged.
- Atomicity via a real MongoDB client-session transaction spanning the guard read
  through both writes — MongoDB's own transaction-conflict detection is the
  compare-and-swap, with the same bounded 5-attempt retry pattern as Redis.
- A named facet's partial update is a single server-side `$set`, not a read-merge-write
  — `DocumentBackend::write` hands the backend the facet's own unmerged fields so
  MongoDB can do the merge in one round trip.
- `MongoDbAdapter` declares `write` / `upsert` / `delete` / `transactions` — genuine
  ACID, the same tier as Postgres.

### Neo4j graph backend (Phase 24)
- `AdapterConfig::Neo4j` — a second graph backend alongside the file adapter, behind
  the new `GraphBackend` seam, reusing `GraphGuard` unchanged.
- A dedicated `__ConduitGuard` node holds guard state, kept separate from projected
  nodes/edges (the same "guard never mixes into your data" rule every adapter follows)
  — and, unlike every other backend, this is structural, not a preference: Cypher can
  only compare-and-set a *direct* node property, not one nested inside a blob, so the
  guard has to be its own node for the CAS to work at all.
- Node deletes use Cypher's native `DETACH DELETE`, cascading to every incident edge's
  own guard tombstone in the same transaction — no separate incident-index bookkeeping
  the way the file adapter needs; the graph structure **is** the incident index.

### MySQL SQL backend (Phase 25)
- `AdapterConfig::MySql` — a third SQL backend alongside SQLite and Postgres, shipped
  as a genuine first-party backend in `kulyrax-core` (a deliberate decision).
- The intended stress test of the Phase 19 `SqlTxn` seam: MySQL's upsert syntax is
  `INSERT … ON DUPLICATE KEY UPDATE`, not `ON CONFLICT … DO UPDATE`. `SqlWrite`'s
  neutral representation generalized to it with one new `Placeholders` variant and one
  new render branch — nothing else about the seam had to change.
- Multi-writer safety mirrors Postgres: a `REPEATABLE READ` transaction with
  `SELECT … FOR UPDATE` on the guard row (a real lock, not a retry loop).

### Backend extension API (Phase 25)
- `SqlTxn`, `KvBackend`, `DocumentBackend`, `GraphBackend` are now `pub` and documented
  as `kulyrax-core`'s stable extension surface — implement one to add a backend for a
  store this repo doesn't ship, without forking the crate.
- `register_adapter_factory(type_name, factory)` — a runtime registry an embedding
  application calls into before `build_adapters_from_config` runs, so `type: mydb` in a
  YAML config resolves through a community factory exactly like a built-in adapter type.
  An unregistered type becomes a per-adapter failure, not a startup crash.
- New guide: **[`docs/writing-a-backend.md`](../docs/writing-a-backend.md)** — which
  trait for which storage kind, the atomicity contract each must satisfy, the guard
  shape as a model (not a requirement), and a full worked example against the MySQL
  backend's real source.

## Behaviour changes — read before upgrading from v0.7.0

- **Three new config variants:** `adapters[].type: redis`, `mongodb`, `neo4j`, `mysql`,
  each with its own `config` block (all support `${ENV_VAR}` expansion in connection
  strings). No change to existing `sqlite`, `postgres`, or `file` configs.
- **New capability declarations:** Redis declares `write`/`upsert`/`delete` (no
  `transactions`); MongoDB, Neo4j, and MySQL each declare
  `write`/`upsert`/`delete`/`transactions` — the same `requires_capabilities`
  vocabulary every mapping already uses.
- **New public API surface on `kulyrax-core`:** the four backend traits
  (`SqlTxn`/`KvBackend`/`DocumentBackend`/`GraphBackend`) and
  `register_adapter_factory` are newly public and are now part of the crate's stable
  extension surface — a breaking change to any of them is a breaking change to the
  crate going forward.
- **New transitive dependencies:** `redis`, `mongodb`, `neo4rs` (plus a direct `tokio`
  dependency for its async-wrapped-in-sync bridge), and `mysql`. `kulyrax-core` now
  pulls in every one of these drivers even if an embedding application uses only
  SQLite — a feature gate to drop unused backends for lean embedded use remains open
  (see `ROADMAP.md`).
- **`AdapterConfig` gained a catch-all `Custom` variant and `StorageKind::Custom`** for
  the registry (Phase 25.2) — only reachable via an unrecognized `type:` string; no
  effect on any existing config.

## Non-Goals (this release)

- No Docker/Kubernetes/sidecar packaging.
- No feature-gated commercial tier — every backend above ships in the open-source
  engine (`architecture.md` §1.4).
- No native Kafka/Kinesis/outbox sources — still open future work on the Phase 17
  `EventSource` trait, unrelated to this release's backend work.
- No real out-of-tree community connector yet. Phase 25 proved the extension point with
  an in-tree MySQL backend built the same way a true external one would be; an actual
  independent crate exercising the registry from outside this repo is still open.
- No benchmarks, no hosted docs site.
- `kulyrax-core` / `kulyrax-cli` are still not published to crates.io under those names
  (both already taken by an unrelated project) — unresolved, carried over from v0.7.0.

Not intended for production use.
