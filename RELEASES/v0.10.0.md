# Kulyrax v0.10.0

## Status

Alpha. This release removes the one-durable-commit-per-event limit for SQLite and
Postgres: each batch of events is one transaction, and Postgres writes each batch in
bulk. It also fixes two MySQL correctness bugs and moves every store's set-up out of
the event path. It contains **breaking changes** for code that embeds `kulyrax-core`
and one new requirement for MySQL servers; see [Upgrading from 0.9](#upgrading-from-09).

---

## Highlights

### Time per stage in every run report
`kulyrax run` reports where time goes: source read, dispatch, each adapter call, schema
set-up, guard reads, writes, commits and checkpoints (`timings` in `--output json`, a
table in text output). `examples/benchmark` uses it to measure every backend.

### Adapters set up their store in an explicit `prepare` step
SQL adapters used to run `CREATE TABLE IF NOT EXISTS` for the guard table inside every
event's transaction; MongoDB and Neo4j created their guard index or constraint on the
first event. All five now do this in `StorageAdapter::prepare`, which `run`, `ingest`,
`replay` and `run --event` call once, before writing anything. `dry-run` never calls
it. A store that can't be set up stops `run` and `ingest` before anything is ingested,
and a reload whose adapters can't be prepared is rejected.

### SQLite and Postgres commit once per batch
The run loop and `replay` already worked in batches; now each adapter that supports it
writes a whole batch in one transaction and commits once, instead of once per event.
Guard lanes are loaded in one query per batch, and Postgres holds one pooled
connection for the batch with its statements prepared once. If any event in a batch
fails, the batch is rolled back and dispatched again one event at a time, exactly as
before, so retries and the dead-letter queue behave as they did. Batches default to
5,000 events (`--max-batch` on `run`, `ingest` and `replay`); in continuous `run` and
`ingest` a batch also closes after `--max-batch-delay-ms` (default 100 ms), whichever
comes first. Other backends still commit per event.

Postgres goes further and writes each batch in bulk: every event is still decided on
its own, in order, but the rows and guard rows it produces are sent as a few
multi-row statements when the batch commits, instead of two statements per event.

### Rebuilds don't slow down with history
Rebuilding a projection into an empty table no longer looks up guards that cannot
exist: an adapter that finds a table with no guard rows reads only the guards of
entities it has written itself since. The directory source lists its files once and
works through them, listing again only when it has caught up, instead of listing the
whole directory on every poll.

## Upgrading from 0.9

### Everyone
- Nothing to change. The guard table, index or constraint is now created at start-up
  rather than on the first event. One side effect: a guard table dropped while
  Kulyrax runs is recreated on the next start or `kulyrax reload`, not on the next
  event.

### Embedding `kulyrax-core`
- **Call `prepare()` before `handle()` on adapters you build yourself.** If you
  construct `SqliteAdapter`, `PostgresAdapter`, `MySqlAdapter`, `MongoDbAdapter` or
  `Neo4jAdapter` directly and call `handle`, call `prepare()` once first; otherwise
  every event fails with "adapter not prepared". Migration: add
  `adapter.prepare()?;` after construction. `KulyraxRuntime`, `run_sources*`,
  `execute_event*` and `ReplayContext` do this for you.
- `StorageAdapter` has a new method, `prepare`, with a default no-op. Custom adapters
  compile and behave unchanged; override it only if your store needs set-up.
- A custom `SqlTxn` backend must create its guard table in its adapter's `prepare`,
  through `sql::exec::ensure_schema`: `sql::exec::project` no longer creates it. See
  `docs/writing-a-backend.md`.
- A custom `Reloader` must hand over adapters that are already prepared.
- New error variants: `SourceError::Prepare` and `PipelineError::AdapterPrepare`.
  Exhaustive matches on those enums need an arm.
- `SourceRunReport` has a new `timings` field; `BatchSummary` a new `fell_back`
  field; `ReplayRunOptions` a new `max_batch` field; `SourceRunOptions` and
  `kulyrax_ingest::ServeOptions` a new `max_batch_delay` field. Struct literals that list
  every field need the new ones (or `..Default::default()`).
- `StorageAdapter` has three new methods, `begin_batch`, `commit_batch` and
  `rollback_batch`, with no-op defaults: custom adapters keep committing per event
  and stay correct. `SqlTxn` has two new methods with defaults: `read_guard_lanes`
  (reads lane by lane) and `has_guard_rows` (answers `true`, so every guard is read).
  `sql::exec::prefetch_guards` takes a `KnownGuards`. See "Batches" in
  `docs/writing-a-backend.md`.

### Operators
- **MySQL needs `binlog_format=ROW` (or `MIXED`) when the binary log is on.** The
  adapter now writes in `READ COMMITTED` transactions, which MySQL cannot log as
  statements. `ROW` is the MySQL 8 default. With `STATEMENT`, `run` and `ingest`
  stop at start-up with an error naming `binlog_format=ROW`, before ingesting
  anything. ([decision](../docs/ledger/decisions/2026-10-28-mysql-read-committed.md))
- The default batch size is 5,000 events (was 256), and in continuous `run` and
  `ingest` a batch closes after at most 100 ms (`--max-batch-delay-ms`), so a quiet
  stream waits at most that long for its batch. A batch holds its database
  transaction, and on Postgres its guard-row locks, until it commits.
- The directory source now splits a file with more events than the batch. While
  such a file is in progress, its checkpoint reads `<file>#<index>`. Files must appear
  in name order: a file named before one already listed is not read.
- **One writer per projection.** An adapter that starts on a target table with no
  guard rows assumes it is that table's only writer. A second Kulyrax writing the same
  table at the same time is not supported (it never was for the same entities).

## Fixes
- **MySQL: a guard write that failed could leave its target row behind.** The guard
  table's `CREATE TABLE IF NOT EXISTS` ran inside each event's transaction, and MySQL
  commits an open transaction on any DDL, so the guard read, target write and guard
  write each committed on their own. They are one transaction again.
- **MySQL: writers adding new entities could deadlock each other** (ERROR 1213), even
  when they projected into different target tables. The guard read
  (`SELECT … FOR UPDATE`) ran under `REPEATABLE READ`, which locks the gap where a
  missing guard row would go, and every projection in a database shares the guard
  table. The MySQL transaction now runs at `READ COMMITTED`, as on Postgres. If your
  MySQL server has the binary log on, it needs `binlog_format=ROW` or `MIXED` (`ROW`
  is the MySQL 8 default); see Operators above.

## Known limitations
- Only SQLite and Postgres batch. MySQL, Redis, MongoDB, Neo4j, Elasticsearch and
  the file stores still commit once per event; batching them, crash-safe file stores
  and an Elasticsearch `_bulk` path are next.
- Rebuilds go through the same guarded write path as live ingest. A dedicated
  rebuild path (load a shadow table, then swap it in) is planned.
- No published benchmarks yet. The numbers in `docs/ledger/` are internal baselines
  from one Windows laptop with the databases in Docker Desktop; published numbers
  will come from a clean Linux machine.
- Kulyrax's own bookkeeping still uses pre-rebrand names (`conduit_projection_state`,
  `.conduit/`, `__ConduitGuard`).
- Release binaries are not code-signed.
