## Behaviour changes

### Events are dispatched in delivery order, never re-sorted by `sequence`

Up to 0.12.1 the run loop sorted every batch by `event.sequence` before dispatch,
and `kulyrax replay` sorted the whole history the same way. `sequence` is per
entity (producer contract §1: different entities have independent sequences), so
the sort reordered *different* entities against each other. The result also
depended on where batches split: the same events gave a different result with
`--max-batch 1`. Two effects of the sort:

- **A graph edge sent after its nodes could land before them.** In Neo4j the
  edge then joined label-less placeholder nodes, and the real nodes were
  created separately: the edge was missing between them, and a node existed
  twice.
- **A child row sent after its parent could be written first** and break a
  foreign key. The batch then failed, and passed only on a retry. A chain deeper
  than the retry budget was dead-lettered or halted the run.

From 0.12.2, events are dispatched in the order the source delivers them, within
a batch and across batches alike. Replay follows sorted file names, then line
order. `sequence` still gates each entity's own lane: redeliveries are skipped
as stale, and under `on_existing: replace` the highest sequence wins whatever
the order.

**What you might notice:** if one entity's events arrived out of order *inside
one batch*, 0.12.1 sometimes repaired them; 0.12.2 does not.
- Under `on_existing: ignore`, a lower-sequence event delivered after a
  higher one is skipped as stale.
- A facet event delivered before its entity's create is skipped
  (`EntityAbsent`). That includes a replay whose files put it first.

Both were already the documented outcome across batches (producer contract §3).
Deliver each entity's events in sequence order. For replay, name the files so
they sort in the order the events happened.
