# Kulyrax v0.12.2

## Status

Alpha. Fixes from the 1.0 senior-engineer review that change behaviour for
current users. Read [Behaviour changes](#behaviour-changes) before you upgrade.
No security fixes: the last security release is
[0.12.1](v0.12.1.md).

## Upgrading from 0.12.1

- **No persisted format changes.** The guards, file stores, checkpoints, batch
  logs and DLQ files written by 0.12.1 are read unchanged, with no migration
  and no rebuild.
- **The gRPC wire format is unchanged** (`ingest.proto` v1).
- **Producers:** deliver each entity's events in sequence order. Give every
  gRPC event a non-empty `position`.
- **Custom `EventSource` implementations:** each batch is now committed at its
  last event. Make that event's position cover the whole batch.

## Behaviour changes

### Events are dispatched in delivery order, never re-sorted by `sequence`

Up to 0.12.1 the run loop sorted every batch by `event.sequence` before dispatch,
and `kulyrax replay` sorted the whole history the same way. `sequence` is per
entity (producer contract §1: different entities have independent sequences), so
the sort reordered *different* entities against each other. The result also
depended on where batches split: the same events gave a different result with
`--max-batch 1`. Two effects of the sort:

- **A graph edge sent after its nodes could land before them.** In Neo4j the
  edge then joined label-less placeholder nodes, and the real nodes were
  created separately: the edge was missing between them, and a node existed
  twice.
- **A child row sent after its parent could be written first** and break a
  foreign key. The batch then failed, and passed only on a retry. A chain deeper
  than the retry budget was dead-lettered or halted the run.

From 0.12.2, events are dispatched in the order the source delivers them, within
a batch and across batches alike. Replay follows sorted file names, then line
order. `sequence` still gates each entity's own lane: redeliveries are skipped
as stale, and under `on_existing: replace` the highest sequence wins whatever
the order.

**What you might notice:** if one entity's events arrived out of order *inside
one batch*, 0.12.1 sometimes repaired them; 0.12.2 does not.
- Under `on_existing: ignore`, a lower-sequence event delivered after a
  higher one is skipped as stale.
- A facet event delivered before its entity's create is skipped
  (`EntityAbsent`). That includes a replay whose files put it first.

Both were already the documented outcome across batches (producer contract §3).
Deliver each entity's events in sequence order. For replay, name the files so
they sort in the order the events happened.

### gRPC acks reach only the producer whose events they cover

Up to 0.12.1, every commit sent one `Ack` to **every** open `Ingest.Stream`. Its
`position` was the batch's text-wise maximum across all producers, and its
`batch_events` and `dlq_events` counted the whole mixed batch. A producer that
resumed from such an ack could resume from another producer's position. With
offsets it compares, it then skipped events Kulyrax had never received.

From 0.12.2, each stream with events in a committed batch receives one ack for
its own events:
- `position` is the position of that stream's last event in the batch, in its
  own send order;
- `batch_events` and `dlq_events` count that stream's events only.

The wire format is unchanged (`ingest.proto` v1), so existing clients keep
working.

**What you might notice:** a stream that sends nothing receives no acks. Before,
it saw every commit. Don't use acks as a liveness signal.

### A batch is committed at its last event, not its highest position

Up to 0.12.1, the run loop committed each batch at the text-wise **maximum**
of its positions, and reported the minimum as `position_from`. From 0.12.2 it
commits at the batch's **last event in delivery order**, and `position_from` /
`position_to` are its first and last positions. Kulyrax no longer compares
positions at all: only the source that made a position orders it (producer
contract §9, new).

For the built-in sources the committed position is the same as before, except
in the directory case below. **What you might notice:** a custom `EventSource`
whose positions don't sort as text (numeric offsets, say `9` then `10`) is now
committed at `10`, where 0.12.1 committed at `9`.

### Empty gRPC positions: a warning now, refused from 1.0

An `EventEnvelope` with an empty `position` is still accepted. Its acks carry
an empty position, so the producer has nothing to resume from.
`kulyrax ingest` now logs a warning once per stream, at the stream's first such
event. **From 1.0 such a stream is refused with `InvalidArgument`.** Give every
event the position your producer resumes from. Note that
`pb::EventEnvelope::from(&Event)` leaves `position` empty: set it.

## Deprecations

- **`SourcePosition`'s `PartialOrd` and `Ord` are removed in 1.0.** They are
  text order, which is not delivery order. Positions are opaque and only their
  own source orders them (producer contract §9). `Eq` stays, and `Hash` is
  added. Rust cannot mark a derived trait impl `#[deprecated]`, so this note
  and the type's documentation are the notice.

## Fixes

### Directory source: a file named after a split file is no longer redelivered forever

A file too large for one batch is taken in parts, at positions
`<file>#<index>`. A later file whose name continues that name with a space,
`!` or `"` (for example `events.ndjson 2.ndjson` after `events.ndjson`) sorts
before those positions as text. Its commit was ignored as "moving backward".
As a result, it was delivered again on every poll, the guards skipped every
repeat as stale, and `kulyrax run --once` never finished. The directory source
now orders its positions by file name and index. The checkpoint format is
unchanged.

### Stdin source: an unreadable checkpoint is an error

A stdin checkpoint that is not a line number was read as line 0. It is now
refused when the source opens, and the error names the source and the value.
