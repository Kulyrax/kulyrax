# Kulyrax v1.0.0-rc.1 (draft)

## Data correctness: check your data

Three bugs in released versions could write wrong data **without an error**.
Each is fixed in this release. Check whether yours met the conditions; if it
did, repair it as described. The guard records each wrongly written event as
projected, so the wrong data stays until you repair it.

### Postgres: values cast to another schema's column types

- **Affected:** v0.12.1 and v0.12.2.
- **Conditions, all needed:**
  - a table with the mapped table's name exists in another schema of the same
    database, visible to Kulyrax's user (schema-per-tenant databases, a
    staging copy beside production, an app schema next to `public`);
  - a column of the same name has a different type there;
  - the events went through the batched path: `kulyrax run` or `ingest` with
    sources (the default);
  - the value was valid under the wrong type, so Postgres's cast accepted it
    into the real column.
- **What it did:** Kulyrax looked up column types by table name in every
  schema and cast the batch's values to the types of whichever table it found
  last. Examples: a timestamp stored in a `text` column came back reformatted
  in UTC (`2026-11-28T10:00:00+05:00` became `2026-11-28 05:00:00+00`); a
  timestamp into `timestamp` could shift by the session time zone, into `date`
  lose its time, a float into `integer` be rounded.
- **Fix:** the table is resolved the way Postgres resolves it (`to_regclass`:
  through `search_path`, or `schema.table` as written), and only its columns
  are read. `table: app.users` now works too; before, it failed every event.
- **Repair:** `kulyrax rebuild` each affected table. A rebuild projects into a
  shadow table with a unique name, then swaps it in.

### Neo4j: edges attached to the wrong nodes, or to none

- **Affected:** every release, v0.9.0 to v0.12.2.
- **Conditions, either:**
  - **two labels share an id value** (integer ids, reused keys): an edge for
    `(:User {id: 1})` was also attached to `(:Org {id: 1})`, and to every
    other node with that id, whatever the order of events;
  - **an edge arrived before its nodes:** it was written between label-less
    placeholder nodes that the real nodes never joined, so they miss it.
    Before 0.12.2, the batch's sort by `sequence` could put an edge first
    even when the producer sent the nodes first; from 0.12.2, only a
    producer that sent the edge first.
- **What it did:** the edge write matched its endpoints by `id` alone, with no
  label: edge mappings had no way to name one.
- **Fix:** an edge mapping now names each end's label, `from_label` and
  `to_label` (required; see "Edge mappings name their endpoints' labels"
  below). An edge that arrives first creates placeholders with those labels,
  which the real nodes merge into.
- **Repair:** clear the Neo4j database and `kulyrax replay` the full history
  into it. There is no graph rebuild. This version refuses to start (exit `4`)
  on a database that holds edges written by an earlier version, since their
  keys lack the labels, and says so.

### File graph store: deleting a node deleted another label's edges

- **Affected:** every release, v0.9.0 to v0.12.2, `type: graph`.
- **Conditions:** two labels share an id value.
- **What it did:** the index a node delete cascades through was keyed by id
  alone, so deleting `Org u1` also deleted `User u1`'s edges. An edge whose
  endpoint shared its id with a deleted node of another label was skipped.
- **Fix:** the index is kept per label and id, and edges name their endpoints'
  labels, as for Neo4j.
- **Repair:** delete the store's root and `kulyrax replay` the full history
  into it. As for Neo4j, this version refuses (exit `4`) a graph store with
  edges written by an earlier version.

### Not silent: edges without `properties`

An edge mapping without `properties` (optional, as the docs' own subgraph
example shows) failed every event on Neo4j: `Expected $properties to be a
map`. Nothing wrong was written; the events were dead-lettered or stopped the
run. (The file graph store wrote the edge, with `null` as its properties.)
Such an edge is now written with no properties, `{}`. Replay the
dead-lettered events.

## Upgrading from 0.12.1

This section also covers 0.12.2: it persists exactly what 0.12.1 does.

**Stop every Kulyrax 0.12 process that writes to a store or database before you
start this version on it.** The first start renames everything Kulyrax persisted
from its old name, `conduit`, to `kulyrax`, in place, once. Then it leaves a
tombstone under the old name, so a 0.12 process started later fails instead of
treating the store as empty and re-applying every event.

| Backend | Before | After | Tombstone under the old name |
|---|---|---|---|
| File stores (document, key-value, graph) | `<root>/.conduit/` | `<root>/.kulyrax/` (same entries inside) | a regular file `<root>/.conduit` |
| SQLite, Postgres, MySQL | table `conduit_projection_state` (Postgres: index `conduit_projection_state_pkey`) | `kulyrax_projection_state` (`kulyrax_projection_state_pkey`) | a view that cannot be written to |
| MongoDB | collection `conduit_projection_state` | `kulyrax_projection_state` | a collection whose validator rejects every document |
| Neo4j | label `__ConduitGuard` and its unnamed constraint | label `__KulyraxGuard`, constraint `kulyrax_guard_key` | none (see below) |
| Redis, Elasticsearch | already `__kulyrax…` | unchanged | not needed |

Every guard lane is kept: an older event redelivered after the upgrade is still
skipped as stale. The CI job `upgrade from 0.12.1` checks this for every backend
with a real 0.12.1 binary.

- **Atomic or resumable.**
  - SQLite and Postgres rename in one transaction.
  - MySQL renames the table and swaps in the tombstone with one `RENAME TABLE`.
  - MongoDB uses `renameCollection`, with the tombstone created under a temporary
    name first.
  - File stores move one entry at a time, each with an atomic rename.
  - Neo4j relabels in batches of 10,000 nodes.

  A process killed during the migration finishes it on its next start.
- **Both names present → refused.** If the old and the new name both exist
  (a 0.12 process wrote after the upgrade, or a backup was restored), start-up
  fails and names both. Keep the one you want, drop or move the other, and start
  again. Nothing is read from both.
- **Several processes on one database** (Postgres, MySQL) upgrade one at a
  time: the migration holds a lock (`pg_advisory_xact_lock`, `GET_LOCK`).
- **Neo4j has no tombstone.** Neo4j Community has no constraint that could stop a
  0.12 process from creating `__ConduitGuard` nodes again. Stop all of them first.
- **File stores last opened by 0.12.0.** A key-value store that 0.12.0 wrote
  keeps its guards in `.conduit/<namespace>/`. Moving those into `.kulyrax/`
  could land them in another owner's entry, so start-up is refused, with the
  paths named. Open the store once with 0.12.1, which moves them, then with this
  version. (0.12.0 is affected by
  [GHSA-6chh-gx4c-448g](https://github.com/Kulyrax/kulyrax/security/advisories/GHSA-6chh-gx4c-448g)
  anyway.)
- **`.kulyrax/` can be shared.** A file store whose `root` is the config folder
  shares `.kulyrax/` with `kulyrax reload` (`control/`) and the scaffolded
  checkpoints (`state/`). Each keeps to its own entries, and a store refuses to
  write anywhere else under `.kulyrax/`.

### Going back to 0.12.1

Stop Kulyrax first. Then, per backend:

- **File stores**: delete the file `<root>/.conduit`, create the directory
  `<root>/.conduit/`, and move `wal`, `lock`, `layout`, `kv`, `entities`, `guard`
  and `incident` from `<root>/.kulyrax/` into it (leave `control` and `state`).
  Write `1` into each file in `.conduit/layout/`.
- **SQLite**:
  `DROP VIEW conduit_projection_state; ALTER TABLE kulyrax_projection_state RENAME TO conduit_projection_state;`
- **Postgres**: the same, plus
  `ALTER INDEX kulyrax_projection_state_pkey RENAME TO conduit_projection_state_pkey;`
- **MySQL**:
  `DROP VIEW conduit_projection_state; RENAME TABLE kulyrax_projection_state TO conduit_projection_state;`
- **MongoDB**:
  `db.conduit_projection_state.drop(); db.kulyrax_projection_state.renameCollection("conduit_projection_state")`
- **Neo4j**: `DROP CONSTRAINT kulyrax_guard_key;` then
  `MATCH (g:__KulyraxGuard) CALL { WITH g SET g:__ConduitGuard REMOVE g:__KulyraxGuard } IN TRANSACTIONS OF 10000 ROWS`.
  0.12.1 recreates its constraint on start.

## A new YAML parser

0.12 read YAML with `serde_yaml` 0.9, which is deprecated and parses through
`unsafe-libyaml`, a machine translation of libyaml (RUSTSEC-2024-0449,
unmaintained). 1.0 reads it with
[serde-saphyr](https://crates.io/crates/serde-saphyr), which is pure Rust with no
`unsafe`. Every config, mapping and routing file goes through one module,
`kulyrax_core::yaml`.

### Your files read the same

No file changes meaning. The parser is configured to read YAML as 0.12 did:
- only `true`/`false` are booleans: `yes`, `on`, `no` are refused where a
  boolean is expected, and are strings elsewhere;
- `0755` is a string, not an octal number;
- `<<` is an ordinary key, not a merge;
- a key repeated in a struct (a mapping's `table:` twice) is refused;
- a key repeated in a map (an event type twice in routing, a column twice in
  `columns:`) keeps the last value.

This was checked before serde_yaml was removed:
- every YAML file in the repository;
- every `yaml` block in its docs;
- every YAML string in its tests (1,700+ reads, including the strings built
  at run time).

Each was read with both parsers, into the real config, mapping and routing
types and into plain values, and the results were identical. A permanent
test keeps the inputs 0.12 refused refused.

### Errors name the file, the field and the line

A mapping with `version: high`, **before** (`kulyrax run`, 0.12.1):

```
Error: Mapping("Invalid YAML in \"mappings\\\\sql\\\\e.yaml\": version: invalid type: string \"high\", expected u32 at line 4 column 10")
```

**After:**

```
Error: Invalid SQL mapping: mappings\sql\e.yaml: field `version`: error: line 4 column 10: invalid u32
 --> <input>:4:10
  |
2 | table: t
3 | primary_key: id
4 | version: high
  |          ^ invalid u32
5 | columns:
6 |   id: payload.id
  |
```

The error names the file, then the field, then the line and column, and
quotes the lines around the error. The CLI now prints errors as text, not as
the debug form `Error: Mapping("…")`. Its exit code is 2 (see "Exit codes" below).

The config, routing and mapping errors now start:
- `failed to parse config: <file>: …`;
- `Invalid routing file: <file>: …`;
- `Invalid <kind> mapping: <file>: …`.

In the config, an error inside one entry of `adapters:` or `sources:` points
at that entry (`field adapters[0]`, its first line), as 0.12's did.

Error text was never part of the stable API. A script that matched serde_yaml's
wording ("invalid type: string …, expected …") needs updating.

### Unknown keys are refused

0.12 ignored a key it did not know, so a misspelt key (`depends_om:`,
`on_exsting:`) silently did nothing. 1.0 refuses it at start-up, in:
- `config.yaml`: the top level, `routing:`, each adapter and source entry, and
  the `config:` blocks of the built-in and Kulyrax-shipped backends;
- every SQL, document, key-value and graph mapping file.

The error names the key, the file, and the line the key is on:

```text
failed to parse config: config.yaml: field `adapters[0]`: line 8: unknown field `depends_om`, expected one of `id`, `priority`, `config`, `capabilities`, `depends_on`
```

A Kulyrax-shipped backend's `config:` block (Postgres, MySQL, Redis, MongoDB,
Elasticsearch, Neo4j, the Postgres outbox) is read by its factory, so its
error names the key and the adapter, without a line:
`postgres adapter "pg": invalid `config`: unknown field `pool_sise`, …`. An
`id:` or `priority:` inside a `config:` block is an unknown key too: they
belong on the entry.

**Before you upgrade,** start 1.0 once against a scratch copy of your project
(`kulyrax run --once`). Every key 0.12 was ignoring shows up as a start-up
error. Delete it, or fix its spelling. No file in Kulyrax's own examples or
docs had one.

### For custom adapters and sources: `raw` is a `serde_json::Value`

`CustomAdapterConfig::raw` and `CustomSourceConfig::raw` were a
`serde_yaml::Value`. They are now a `serde_json::Value`, so serde_yaml is no
longer part of Kulyrax's API.

The usual way to read your block, `backend_config()` / `source_config()`, is
unchanged:

```rust
// 0.12 and 1.0
let cfg: MyConfig = entry.backend_config()?;
```

Code that read `raw` directly changes like this:

```rust
// 0.12
let url = entry.raw.get("config").and_then(|c| c.get("url")).and_then(serde_yaml::Value::as_str);
let cfg: MyConfig = serde_yaml::from_value(entry.raw.clone())?;

// 1.0
let url = entry.raw.get("config").and_then(|c| c.get("url")).and_then(serde_json::Value::as_str);
let cfg: MyConfig = serde_json::from_value(entry.raw.clone())?;
```

Tests that build an entry by hand write `raw: serde_json::json!({ … })`, where
they used to call `serde_yaml::to_value(…)`.

Two YAML shapes have no JSON form:
- a key that is not a string (`1: x`) arrives as a string (`"1"`), as it did
  through serde_yaml;
- a non-finite float (`.inf`, `.nan`) in a custom block is refused at start-up,
  with the file, field and line. 0.12 passed it to the factory as a YAML float.

## Edge mappings name their endpoints' labels

A node is its label and its id: `User u1` and `Org u1` are different nodes.
An edge mapping now says which labels its ends have, with two required keys
(the fix for the graph bugs under "Data correctness" above):

```yaml
kind: edge
event: UserFollowed
edge_type: FOLLOWS
from_label: User        # new, required
to_label: User          # new, required
from: payload.follower_id
to: payload.followee_id
version: 1
```

The same goes for each `kind: edge` record of a `kind: subgraph`. A mapping
without them is refused when the mappings load (exit `2`), naming the file and
the key. Both backends use the labels:
- **Neo4j** writes the edge with
  `MERGE (a:<from_label> {id}) MERGE (b:<to_label> {id})`, so an edge that
  arrives before its nodes creates labelled placeholders, and the nodes merge
  into them.
- **The file graph store** indexes the edge under each end's label and id, so
  deleting a node deletes its own edges only.

An edge's identity is now `[edge_type, from_label, from, to_label, to]`, plus
its `discriminator`. A graph store with edges keyed the old way cannot be
read; see "Versioned formats" below.

An edge mapping without `properties` now writes the edge with none; it failed
on Neo4j before.

## API changes

### Public enums and structs are `#[non_exhaustive]`

Every public enum is `#[non_exhaustive]`, as is every public struct with public
fields that is part of the stable API: `Event`, reports, outcomes, guards, plans,
mappings, `KulyraxConfig`, the run options. So a variant or field added in 1.x
is not a breaking change. Two things change in your code.

**A `match` on a Kulyrax enum needs a wildcard arm:**

```rust
// 0.12
match outcome {
    AdapterOutcome::Created => …,
    AdapterOutcome::Updated => …,
    AdapterOutcome::Deleted => …,
    AdapterOutcome::Skipped { reason } => …,
    AdapterOutcome::Failed => …,
}

// 1.0
match outcome {
    AdapterOutcome::Created => …,
    // …
    AdapterOutcome::Failed => …,
    _ => …, // a variant added later
}
```

**You build these types with constructors, not struct literals:**

```rust
// 0.12
let event = Event {
    event_id: "e1".into(),
    event_type: "UserCreated".into(),
    payload: r#"{"id":"u1"}"#.into(),
    metadata: HashMap::new(),
    version: 1,
    sequence: 1,
};

// 1.0
let event = Event::new("e1", "UserCreated", 1, r#"{"id":"u1"}"#);
// optional: .with_metadata(map) .with_version(2)
```

| 0.12 literal | 1.0 |
|---|---|
| `Event { … }` | `Event::new(event_id, event_type, sequence, payload)`, `.with_metadata(…)`, `.with_version(…)` |
| `SourcedEvent { event, position }` | `SourcedEvent::new(event, position)` |
| `KulyraxConfig { version: 1, routing: RoutingConfig { file }, adapters, … }` | `KulyraxConfig::new(file, adapters)`, `.with_failure_policy(…)`, `.with_migration_policy(…)`, `.with_sources(…)` |
| `RoutingConfig { file }` | `RoutingConfig::new(file)` |
| `SourceRunOptions { … }`, `ReplayRunOptions { … }`, `MappingSet { … }`, `ServeOptions { … }` | `let mut o = SourceRunOptions::default();` then assign the fields |
| `GuardState { … }`, `GraphFacetGuard { … }`, `GuardFingerprint { … }`, `ShadowTable { … }` | `::new(…)` with the same fields, in order |
| `AdapterBuildContext { … }`, `SourceBuildContext { … }` | `::new(…)` with the same fields, in order |
| `DocumentPlan { …projection's fields… }`, `KvPlan { … }` | `DocumentPlan::from(projection)`, `KvPlan::from(projection)` |

Reading the fields is unchanged.

### Adapters are built with `from_config`

Each adapter's positional `new(…)` (6 to 9 arguments) is hidden. The public
constructor is `from_config(&cfg, &AdapterBuildContext)`, which runs the same
checks as building from YAML.
- **`cfg` is `#[non_exhaustive]`**, built with `new(<required fields>)` and a
  `with_*` setter for each other field.
- **The context carries the run's mappings, upcasters and migration policy**,
  as it already did for registry factories.

```rust
// 0.12
let redis = RedisAdapter::new(
    "cache".into(), &url, 8, 2,
    KvRuntimeBuilder::new(mappings.kv.clone()),
    Arc::clone(&upcasters), MigrationPolicy::Strict,
);

// 1.0
let ctx = AdapterBuildContext::new(mappings, upcasters, MigrationPolicy::Strict);
let cfg = RedisConfig::new(url).with_id("cache").with_priority(2).with_pool_size(8);
let redis = RedisAdapter::from_config(&cfg, &ctx)?;
```

| Adapter | `cfg` |
|---|---|
| `PostgresAdapter`, `MySqlAdapter`, `RedisAdapter` | `PostgresConfig::new(url)` (and so on), `.with_pool_size(n)` |
| `MongoDbAdapter` | `MongoDbConfig::new(url, database)`, `.with_pool_size(n)` |
| `ElasticsearchAdapter` | `ElasticsearchConfig::new(url)`, `.with_username(…)`, `.with_password(…)`, `.with_timeout_ms(…)` |
| `Neo4jAdapter` | `Neo4jConfig::new(uri, user, password)`, `.with_database(…)` |
| `SqliteAdapter` | `SqliteAdapterConfig::new(id, priority, SqliteConfig::new(path))` |
| `FileDocumentAdapter`, `FileKvStore`, `GraphStore` | `FileAdapterConfig` / `KeyValueAdapterConfig` / `GraphAdapterConfig::new(id, priority, …Config::new(root))` |

Each networked config also has `.with_id(…)` and `.with_priority(…)`. In YAML
those two stay on the adapter's entry, not in its `config:` block. Each built-in
entry has `.with_capabilities(…)` and `.with_depends_on(…)`.

The other config structs are `#[non_exhaustive]` too, with constructors:
- `CustomAdapterConfig::new(type_name, id, priority, raw)`;
- `CustomSourceConfig::new(type_name, id, raw)`, with `.with_state_dir(…)`;
- `DirectorySourceConfig::new(id, path, state_dir)`;
- `StdinSourceConfig::new(id, state_dir)`;
- `OutboxConfig::new(url, table, sequence_column)`, with a `with_*` for each
  other key;
- `OutboxColumns::default()`, with a `with_*` for each column.

### One path per type; internals hidden

Each public type has one canonical path: the module that defines it. The crate
root also re-exports the front door (`KulyraxRuntime`, `ExecutionReport`,
`EventSource`, `run_sources`, …), as in the README.

- **Other re-exports are `#[doc(hidden)]`**: for example `runtime::DryRunReport`
  (canonical `runtime::dry_run::DryRunReport`) and `execution::ExecutionStatus`.
  They still compile, but are outside semver and may go in a minor release.
- **Internals are hidden or crate-private** (`docs/stability.md` §1): `dispatch`,
  `batch`, `scaffold`, the file store, the loaders, and others.
- **The storage kinds' re-exports are removed.** A backend author imports from
  `exec`:

```rust
// 0.12
use kulyrax_core::adapter::sql::{SqlTxn, SqlWrite};
use kulyrax_core::adapter::document::DocumentBackend;
// 1.0
use kulyrax_core::adapter::sql::exec::{SqlTxn, SqlWrite};
use kulyrax_core::adapter::document::exec::DocumentBackend;
```

The same holds for `graph::exec` (`GraphBackend`, `NodePlan`, `EdgePlan`, …) and
`keyvalue::exec` (`KvBackend`, `KvPlan`, …). They are removed, not hidden,
because a hidden re-export makes semver tooling treat these traits as sealed,
and a backend author has to implement them.

Two more internals went:
- **`replay::EventsFromPath` is opaque.** It was an enum whose variants exposed
  the iterator's state (`Directory { paths, index }`, `Ndjson { reader, line }`,
  …). It is now a struct with private fields. Build it with
  `replay::events_from_path` and iterate it, as before; code that matched on
  the variants no longer compiles.
- **`runtime::error::RuntimeError` is removed**, with its module. Nothing in
  Kulyrax returned it.

### Source positions are unordered, and a gRPC position is required

- **`SourcePosition`** derives `Eq` and `Hash`, and no longer derives
  `PartialOrd` or `Ord`. Its text order was never delivery order (`"9"` sorts
  after `"10"`). A source that orders its own positions parses them by its own
  rule (producer contract §9).
- **An event with an empty `position` ends its gRPC stream with
  `INVALID_ARGUMENT`.** 0.12.2 accepted it with a warning. The events the stream
  sent before it keep their acks.
- **`pb::EventEnvelope::from(&Event)` is gone**: it left the position empty.
  Build the client's envelope with its position instead (next section).

### The gRPC crates use their own types, not generated ones

The frozen contract is `proto/kulyrax/v1/ingest.proto`. The tonic/prost code
generated from it (`kulyrax_client::pb`, `kulyrax_ingest::pb`) is now private,
so a tonic or prost upgrade never forces a major release. A build that needs it
turns on the `unstable-pb` feature, which is outside semver.

`kulyrax_client` has its own types: `EventEnvelope`, `Ack`, `AckOutcome`,
`ClientError`, `RpcError` and `StatusCode`. `Producer`'s methods are unchanged.

```rust
// 0.12: the generated struct, built field by field
producer.send(EventEnvelope {
    event_type: "UserRegistered".into(),
    payload: payload.clone(),
    metadata: HashMap::new(),
    version: 1,
    sequence,
    position: position.into(),
    event_id: String::new(),
}).await?;

// 1.0
producer.send(EventEnvelope::new("UserRegistered", payload, sequence, position)).await?;
// optional: .with_metadata(map) .with_version(2) .with_event_id("e1")
```

`ClientError::Rpc` used to hold a `Box<tonic::Status>`. It now holds an
`RpcError { code: StatusCode, message }`:

```rust
// 0.12
Err(ClientError::Rpc(status)) if status.code() == tonic::Code::InvalidArgument => …
// 1.0
Err(ClientError::Rpc(e)) if e.code == StatusCode::InvalidArgument => …
```

### Errors: `Send + Sync`, typed causes, one rename

Every public error is `std::error::Error + Send + Sync + 'static`, so it fits
`Box<dyn Error + Send + Sync>`, `anyhow` and threads. `source()` now returns
the cause wherever it is a YAML, JSON or I/O error. The text each error prints
is unchanged.

| 0.12 | 1.0 |
|---|---|
| `PipelineError::ConfigParse(String)` | `ConfigParse(YamlError)`: its `file()` and `field()`, and `source()` |
| `PipelineError::EventParse(String)` | `EventParse(serde_json::Error)` |
| `PipelineError::Mapping(String)`, `Routing(String)` | `Mapping(LoadError)`, `Routing(LoadError)`: `Parse { context, source: YamlError }`, `Read { context, source: io::Error }` or `Invalid(String)` |
| `ReplayLoadError::Json(String)` | `Json { file: Option<PathBuf>, source: serde_json::Error }` |
| `DependencyOrderError` (no `Display`) | implements `Display` and `Error` |
| `AdapterReportError` | renamed **`AdapterFailure`**: the report's record of a failed write, not an error. Its variants and JSON are unchanged |

```rust
// 0.12
Err(PipelineError::ConfigParse(msg)) => eprintln!("{msg}"),
// 1.0
Err(PipelineError::ConfigParse(e)) => eprintln!("{e} (in {:?})", e.file()),
```

The adapters' `WriteFailed` / `ExecutionFailed` and `FactoryConfigInvalid`
still hold a message, not the driver's error. That text went through
redaction, and a raw driver error can print the connection URL with its
password.

## Versioned formats

Everything Kulyrax persists and reads back now records its version, so that a
later Kulyrax can refuse what it cannot read instead of misreading it
([stability §5](../docs/stability.md#5-persisted-formats)).

**What appears in your stores.** On its first start, each store gets one small
format marker beside Kulyrax's guards:

| Backend | Marker |
|---|---|
| File stores | the existing layout marker `.kulyrax/layout/<kind>` now holds the version: `2` for `kv` and `document`, `3` for `graph` |
| SQLite, Postgres, MySQL | table `kulyrax_format (component, version)`, in the guard table's schema or database |
| MongoDB | collection `kulyrax_format`, document `{_id: "guards", version: 1}` |
| Redis | hash `__kulyrax:format`, field `guards` = `1`, one per Redis database |
| Elasticsearch | index `kulyrax_format`, document `guards`, one per cluster |
| Neo4j | node `(:__KulyraxFormat {component: 'guards', version: 2})` and its constraint `kulyrax_format_component` |

Source checkpoints and the Postgres outbox state gain a `"format": 1` field;
a batch log's magic `KLXWAL01` already carried its version.

**Upgrading needs nothing,** except for graph stores with edges (below). A
store or checkpoint written by 0.12.x has no version: it is read as format 1
and stamped on its first start or commit.

**Graph stores with edges are refused (exit `4`).** Earlier versions keyed an
edge without its endpoints' labels, which were never stored, so this version
cannot rebuild the keys. A Neo4j database or file graph store from 0.12.x
that holds edges is refused at start, with the store named and the repair:
clear it and `kulyrax replay` the full history. You need that replay anyway
if the graph bugs under "Data correctness" could have hit you. A graph store
with nodes only is stamped with the current format (Neo4j `2`, file `3`) and
opens as it is.
Going back to 0.12.1 still works as described above. 0.12.1 ignores the
markers and the new `format` fields; leave them in place.

**What can now refuse to start (exit `4`).**
- A store, checkpoint or batch log written by a newer Kulyrax. The error names
  it and both versions, and nothing is read, replayed or written first.
- Content that is not a Kulyrax format, for example a layout marker that is not
  a number. It is left as it is.
- A marker that could not be created: the error names the store and the grant
  it needs. See [required grants](../docs/required-grants.md); for SQL it is
  the CREATE right Kulyrax already needed for its guard table.

**Fixes.**
- **A batch log with an unknown magic number was deleted.** A file store
  treated the newest `.kulyrax/wal/*.log` whose magic it did not recognise as
  half-written and deleted it, losing that batch. A log only gets its name
  after its content is synced, so such a log is never crash damage. It is now
  refused (exit `4`) and kept, whatever its position.
- **SQLite: concurrent first starts could fail** with `database is locked`
  when several adapters or processes opened a new database at once. Fixed.
- **File stores: two adapters sharing a store root** in one process could set
  it up at the same time, one checking its layout while the other was still
  replaying batch logs. Set-up is now one at a time.
- **New file stores wrote layout marker `1`**, and stores migrated from 0.12.1
  wrote `2`, for the same layout. Both are now `2`. A `1` or an empty marker is
  read as `2` and rewritten.

**Names Kulyrax keeps for itself are refused (exit `2`).** A mapping file whose
target is one of Kulyrax's own objects is refused when the mappings load,
naming the file, the key and the name:
- SQL tables `kulyrax_projection_state`, `kulyrax_format`,
  `conduit_projection_state`, `kulyrax_tombstone_tmp`, and `*__kulyrax_rebuild`
  (without case);
- the same four as document collections or indexes;
- document fields `__kulyrax*`, key-value namespaces `__kulyrax*`, graph labels
  `__Kulyrax*` and `__Conduit*`.

Such a mapping would have written into Kulyrax's guards, marker or tombstone.
0.12 accepted it, except a table named like a rebuild shadow: that one
`rebuild` refused (exit `4` in 1.0's codes) and now load refuses (exit `2`).
Rename the target. The list is in
[mapping reference, Names](../docs/mapping-reference.md#names-kulyrax-keeps-for-itself).

**Redis: the eviction policy.** Kulyrax's Redis store requires
`maxmemory-policy noeviction`, or `volatile-*` with no TTL on Kulyrax keys:
an evicted guard or marker silently loses data. At start, a Redis adapter
reads the policy once:
- an `allkeys-*` policy prints a `WARNING:` line naming it;
- a policy that cannot be read (managed Redis often blocks `CONFIG`) prints
  one line saying what is required.

Neither refuses the start.

**For code that embeds Kulyrax.**
- `SqlTxn` has a new required method, `ensure_format_marker`: an out-of-tree
  SQL backend must implement it ([writing a backend](../docs/writing-a-backend.md#the-format-marker)).
- `GraphBackend` names nodes by label and id everywhere:
  - `node_is_tombstoned(label, node_id)` takes the label;
  - `write_edge(&EdgeRef, properties, guard)` and
    `delete_edge(&EdgeRef, guard)` take an `EdgeRef` (`edge_type`,
    `from_label`, `from`, `to_label`, `to`, `key`) instead of separate
    arguments;
  - `GraphEdgeMapping`, `EdgePlan` and `ResolvedRecord::Edge` have
    `from_label` and `to_label`.
- New error variants carry the refusal, typed:
  - `AdapterError::Format`, `SourceError::Format`, `SqlError::Format`,
    `DocumentError::Format`, `GraphError::Format`;
  - all of them hold a `kulyrax_core::format::FormatError`.
- `PrepareFailure` has a new field `refused`, true for a format refusal.
- `source::checkpoint::Checkpoint` has a new field `format`.
- `ElasticsearchAdapter` now has a `prepare`, which checks the marker. Call
  `StorageAdapter::prepare` before projecting, as the runtime does.

## Exit codes

0.12 exited `1` for every failure. 1.0 says which kind it was, and these codes
are frozen:

| Code | Meaning |
|---|---|
| `0` | success |
| `1` | internal or unexpected error (I/O, a database that failed, an adapter that could not be prepared) |
| `2` | invalid input: bad arguments, a config, mapping or routing file that does not parse, has an unknown key or fails validation, a mapping that targets a name Kulyrax keeps for itself, a bad event file, a factory refusing its config, a `rebuild` of an adapter that cannot be rebuilt, a `reload` refused for an invalid config |
| `3` | events failed or were dead-lettered (`run --event`, `run --once`, `replay`, `rebuild`, `dry-run`) |
| `4` | refused by a safety check: a source's lock or a file store's lock is held, a `rebuild` refused before it started or at the swap, `init` would overwrite a file, a store or checkpoint in a format this version does not read, or a format marker that could not be created (see [Versioned formats](#versioned-formats)). Nothing was changed |

What changes for a script that checks them:
- **"Did any event fail?"** is now `[ $? -eq 3 ]`. A `--once` run that
  dead-lettered every failure used to exit 0 and now exits 3. A continuous `run`
  or `ingest` still exits 0 for failures it dead-lettered.
- **A `reload` refused for an invalid config** exits 2. A `reload` that no
  running process answered exits 1 (it was 2).
- **`init` into a folder with a starter file already there** exits 4.
- **A file store another process holds** (its `.kulyrax/lock`) exits 4, as a
  held source lock does. Rc.1 drafts before this said 1. For code that embeds
  Kulyrax: it is `AdapterError::Locked`, and `PrepareFailure::refused` is true.
- **`set -e` scripts** see the same thing: any non-zero code is still a
  failure.

```sh
# 0.12
kulyrax run --config c.yaml --mappings m --once || echo "something failed"
# 1.0
kulyrax run --config c.yaml --mappings m --once
case $? in
  0) ;;
  3) echo "events failed; see the DLQ" ;;
  4) echo "refused: another process holds the source" ;;
  *) echo "invalid project or internal error" ;;
esac
```
