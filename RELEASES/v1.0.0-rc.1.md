# Kulyrax v1.0.0-rc.1 (draft)

## Upgrading from 0.12.1

This section also covers 0.12.2: it persists exactly what 0.12.1 does.

**Stop every Kulyrax 0.12 process that writes to a store or database before you
start this version on it.** The first start renames everything Kulyrax persisted
from its old name, `conduit`, to `kulyrax`, in place, once. Then it leaves a
tombstone under the old name, so a 0.12 process started later fails instead of
treating the store as empty and re-applying every event.

| Backend | Before | After | Tombstone under the old name |
|---|---|---|---|
| File stores (document, key-value, graph) | `<root>/.conduit/` | `<root>/.kulyrax/` (same entries inside) | a regular file `<root>/.conduit` |
| SQLite, Postgres, MySQL | table `conduit_projection_state` (Postgres: index `conduit_projection_state_pkey`) | `kulyrax_projection_state` (`kulyrax_projection_state_pkey`) | a view that cannot be written to |
| MongoDB | collection `conduit_projection_state` | `kulyrax_projection_state` | a collection whose validator rejects every document |
| Neo4j | label `__ConduitGuard` and its unnamed constraint | label `__KulyraxGuard`, constraint `kulyrax_guard_key` | none (see below) |
| Redis, Elasticsearch | already `__kulyrax…` | unchanged | not needed |

Every guard lane is kept: an older event redelivered after the upgrade is still
skipped as stale. The CI job `upgrade from 0.12.1` checks this for every backend
with a real 0.12.1 binary.

- **Atomic or resumable.**
  - SQLite and Postgres rename in one transaction.
  - MySQL renames the table and swaps in the tombstone with one `RENAME TABLE`.
  - MongoDB uses `renameCollection`, with the tombstone created under a temporary
    name first.
  - File stores move one entry at a time, each with an atomic rename.
  - Neo4j relabels in batches of 10,000 nodes.

  A process killed during the migration finishes it on its next start.
- **Both names present → refused.** If the old and the new name both exist
  (a 0.12 process wrote after the upgrade, or a backup was restored), start-up
  fails and names both. Keep the one you want, drop or move the other, and start
  again. Nothing is read from both.
- **Several processes on one database** (Postgres, MySQL) upgrade one at a
  time: the migration holds a lock (`pg_advisory_xact_lock`, `GET_LOCK`).
- **Neo4j has no tombstone.** Neo4j Community has no constraint that could stop a
  0.12 process from creating `__ConduitGuard` nodes again. Stop all of them first.
- **File stores last opened by 0.12.0.** A key-value store that 0.12.0 wrote
  keeps its guards in `.conduit/<namespace>/`. Moving those into `.kulyrax/`
  could land them in another owner's entry, so start-up is refused, with the
  paths named. Open the store once with 0.12.1, which moves them, then with this
  version. (0.12.0 is affected by
  [GHSA-6chh-gx4c-448g](https://github.com/Kulyrax/kulyrax/security/advisories/GHSA-6chh-gx4c-448g)
  anyway.)
- **`.kulyrax/` can be shared.** A file store whose `root` is the config folder
  shares `.kulyrax/` with `kulyrax reload` (`control/`) and the scaffolded
  checkpoints (`state/`). Each keeps to its own entries, and a store refuses to
  write anywhere else under `.kulyrax/`.

### Going back to 0.12.1

Stop Kulyrax first. Then, per backend:

- **File stores**: delete the file `<root>/.conduit`, create the directory
  `<root>/.conduit/`, and move `wal`, `lock`, `layout`, `kv`, `entities`, `guard`
  and `incident` from `<root>/.kulyrax/` into it (leave `control` and `state`).
  Write `1` into each file in `.conduit/layout/`.
- **SQLite**:
  `DROP VIEW conduit_projection_state; ALTER TABLE kulyrax_projection_state RENAME TO conduit_projection_state;`
- **Postgres**: the same, plus
  `ALTER INDEX kulyrax_projection_state_pkey RENAME TO conduit_projection_state_pkey;`
- **MySQL**:
  `DROP VIEW conduit_projection_state; RENAME TABLE kulyrax_projection_state TO conduit_projection_state;`
- **MongoDB**:
  `db.conduit_projection_state.drop(); db.kulyrax_projection_state.renameCollection("conduit_projection_state")`
- **Neo4j**: `DROP CONSTRAINT kulyrax_guard_key;` then
  `MATCH (g:__KulyraxGuard) CALL { WITH g SET g:__ConduitGuard REMOVE g:__KulyraxGuard } IN TRANSACTIONS OF 10000 ROWS`.
  0.12.1 recreates its constraint on start.
