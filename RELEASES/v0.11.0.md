# Kulyrax v0.11.0

## Status

Alpha. This release makes the file-backed stores (document, key-value, graph)
**crash-safe and batched**: a crash, an OS crash or a power loss no longer loses or
tears a projection, and each batch is made durable with one fsync instead of none.
It also **batches every other backend**: MySQL, Redis, MongoDB, Neo4j and
Elasticsearch now commit once per batch instead of once per event. It contains
small **breaking changes** for code that embeds `kulyrax-core`, a new
**single-writer rule** for file stores, a **MySQL guard-table change** (entity keys
become case-sensitive), and a new minimum Rust version (1.89); see
[Upgrading from 0.10](#upgrading-from-010).

---

## Highlights

### Crash-safe file stores
Until now the file stores wrote each event straight to its data and guard files with
no fsync, and the source checkpoint was not fsynced either. After an OS crash or a
power loss, the checkpoint could survive while the projections it covered did not,
and those events were never projected again. A process crash in the middle of an
event could leave a new data file next to an old guard.

Now each file store writes a batch like this:

1. Every event is decided in memory, as before. A key written several times in a
   batch keeps only its final content.
2. The whole batch, data and guards, is written to one **batch log**
   (`.conduit/wal/<n>.log`, with a length and a CRC-32) and fsynced once.
3. The batch is applied to the per-key files, without fsync.
4. The source checkpoint is written: temp file, fsync, rename, directory fsync.
5. In the background, once the batches are 2 s old, a **sync point** fsyncs each
   file they touched (once per file), then deletes their logs.

At start-up, each file store replays any batch log still on disk before ingesting
anything. A torn newest log (a crash during its write) is discarded, and its events
are read again from the source. Details, costs and assumptions:
[`docs/file-store-durability.md`](../docs/file-store-durability.md).

Tested by crashing the real binary at each step of the commit path, by truncating a
log, by wiping every file not yet synced, and by killing it at random 20 times, each
time comparing every file with a run that never crashed.

### File stores commit once per batch
The file stores now implement `begin_batch` / `commit_batch` / `rollback_batch`. A
rolled-back batch leaves nothing on disk, and a failed event leaves nothing of
itself. Guards are cached in memory. On a store that starts empty, a guard that
isn't cached is known to be absent without reading the disk.

Throughput, 100,000 events, batch 5,000, one Windows laptop (internal baseline, not
a published benchmark):

| Store | v0.10 | v0.11 |
|---|---|---|
| Document | 393 events/s | 944 events/s |
| Key-value | 430 events/s | 859 events/s |
| Graph | 360 events/s | 849 events/s |

Store directory excluded from Microsoft Defender's real-time scan in both columns.
About 95% of v0.11's time is spent writing the per-key files (two new files per
event); the batch log, checkpoint and sync point take the rest. With Defender
scanning the directory, every store drops to 230–280 events/s.

None of the three keeps up with 1,000 events/s sustained on this laptop: after
3 minutes, p99 lag is 60–67 s and still growing.

### Time per stage for the file stores
`kulyrax run`'s stage table has three new rows: `log` (writing and fsyncing the batch
log), `apply` (writing the per-key files) and `sync` (sync points, which run in the
background).

### Every networked backend commits once per batch
v0.10 batched SQLite and Postgres. The rest now do too:

| Backend | Per batch |
|---|---|
| MySQL | one `READ COMMITTED` transaction; guard lanes loaded and locked up front, one query per table |
| MongoDB | one transaction; every guard read inside it, one `$in` query per collection; each entity's writes collapsed to one document operation and one guard write |
| Neo4j | one transaction; every event's Cypher, compare-and-set included, runs in it |
| Redis | guards `WATCH`ed and loaded with `MGET`; one `MULTI`/`EXEC` with each entity's final state |
| Elasticsearch | documents loaded with one `_mget`; one `_bulk` request with each document's final state, version-checked |

Concurrent writers stay safe: another writer's change to an entity the batch read
fails the batch's commit (a lock, a write conflict, an aborted `EXEC` or a 409),
and the batch is re-dispatched one event at a time, with each backend's usual
retry. Each backend's tests check that a batch leaves exactly what one event at a
time leaves, against a real server. Throughput was not measured for this release.

The Elasticsearch suite now runs in CI (`test (elasticsearch)`); it never did before.

### `kulyrax rebuild`: re-project a SQL adapter's history in place
After a mapping change, or to repair a projection:

```sh
kulyrax rebuild --config config.yaml --mappings mappings --events history/ --adapter sql
```

Every table the adapter's SQL mappings write is rebuilt from the full history in a
shadow table (`<table>__kulyrax_rebuild`, with the table's columns, keys and
indexes). Readers keep the current tables meanwhile. At the end, one transaction
replaces each table and its guard lanes with the shadow's, so readers see either
the old projection or the new one. Only that adapter is written.

**Stop every other writer to those tables first.** The rebuild checks, with the
tables locked, that their guard lanes are as it found them when it started; if
anything projected into them meanwhile, the swap is refused and nothing changes.
If an event fails, nothing is swapped and the shadow tables are left for
inspection. Tables the swap would break are refused before anything is created,
each object named: on Postgres a dependent view, a foreign key into or out of the
table, or a `serial` / identity column; on SQLite a view or trigger that uses the
table, or a foreign key pointing at it. SQLite and Postgres; MySQL commits table DDL implicitly, so it cannot
swap atomically and is refused.

### Several graph records from one event (`kind: subgraph`)
A graph mapping can now write a node and its edges, or any list of nodes and
edges, from one event:

```yaml
kind: subgraph
event: OrderPlaced
version: 1
records:
  - { kind: node, label: Order, key: payload.order_id, properties: { total: payload.total } }
  - { kind: node, label: Customer, key: payload.customer_id, properties: { name: payload.name } }
  - { kind: edge, edge_type: PLACED, from: payload.customer_id, to: payload.order_id }
```

Each record is an ordinary node or edge mapping with its own guard lane; all of
an event's records are applied in one transaction, on the file graph store and
on Neo4j, so a failing record leaves nothing of the event behind. See
[`docs/mapping-reference.md`](../docs/mapping-reference.md#graph-mappingsgraph).

## Upgrading from 0.10

### MySQL: entity keys are now case-sensitive
`K` and `k` are now **separate entities**. Under the server's default collation
they shared one guard lane, so an event for one could be skipped as stale because
of the other. The guard table's key columns (`target_table`, `entity_key`, `facet`
of `conduit_projection_state`) are now `utf8mb4_bin`, as SQLite and Postgres
compare keys; the first start under 0.11 converts an existing table once
(`ALTER TABLE`, rows kept). If you depend on case-insensitive identity, normalize
the key in the producer or the mapping. The conversion rebuilds the guard table:
with several Kulyrax processes on one MySQL database, upgrade them together, or
expect a few events to fail with ERROR 1213 and be retried while it runs.

### Everyone
- **Rust 1.89 or newer** to build from source (was 1.88), for `File::try_lock`.
- Nothing to change in config or mappings. A file store's first start under 0.11
  creates `.conduit/wal/` and `.conduit/lock` in its root.

### Operators
- **One process per file store.** Each file store locks `.conduit/lock` when it
  starts. A second Kulyrax process on the same store directory now stops at start-up
  with "file store … is in use by another process". Two processes writing one store
  were never safe; now it is refused. Within one process, `kulyrax reload` keeps
  working. A document store and a key-value store can still share one root.
- Expect up to about 3 s of recent batches in `.conduit/wal/` while running. They
  are deleted at each sync point and at a clean shutdown. Don't delete them by hand:
  they are what recovery replays.
- If start-up fails with "batch log … is corrupt and newer batch logs exist", the
  disk returned bad data. A crash cannot cause this. Keep the logs for inspection,
  and rebuild the store from the event log.
- Each batch now costs one fsync per file adapter plus one for the checkpoint.
  Prefer large batches (the default 5,000) for file stores.
- Files written before 0.11 were never fsynced. A store that was running during an
  OS crash or power loss under 0.10 may hold torn files: rebuild it if in doubt.
- Batches hold their transaction, and with it the touched entities' locks, until
  the batch commits (MySQL, MongoDB, Neo4j, as SQLite and Postgres since 0.10). A
  second writer on the same entities waits longer than before.

### Embedding `kulyrax-core`
- `StageTimings` has three new fields, `log`, `apply` and `sync`, and `Stage` three
  new variants. Exhaustive matches and struct literals need them.
- New function `kulyrax_core::execution::stages::record`.
- New public module `kulyrax_core::adapter::file_store` (`FileStore`, `FileTxn`),
  the durable write path the file adapters share.
- File adapters you build yourself may call `prepare()` before `handle()`, as with
  every other adapter. If you don't, they prepare themselves on first use (lock and
  recovery) and keep working as before.
- `source::checkpoint::write_checkpoint` now fsyncs. It is slower: one fsync per
  call.
- Rebuilds: new module `kulyrax_core::rebuild` (`rebuild`, `RebuildReport`,
  `ShadowRebuild`), `pipeline::rebuild`, and `StorageAdapter::shadow_rebuild`
  (default `None`). `SqlTxn` has five new methods for it, with defaults, so
  existing backends compile unchanged and report rebuilds as unsupported.
- `PipelineError` has a new variant, `Rebuild`. Exhaustive matches need it.
- Graph: `GraphMapping` has a new variant, `Subgraph(GraphSubgraphMapping)`, and
  `DryRunOutcome` one, `PlannedSubgraph`. New: `GraphMapping::records`,
  `GraphRuntimeBuilder::build_all`, `graph::exec::{project_record, project_all,
  combined_outcome}`. `GraphRuntimeBuilder::build` refuses a subgraph mapping.

### Coming from 0.8 or earlier: database drivers left `kulyrax-core` (v0.9)
Nothing changes here between 0.10 and 0.11; this repeats a **v0.9.0** change for
anyone skipping releases ([notes](v0.9.0.md#every-networked-backend-is-its-own-crate)).
`kulyrax-core` no longer pulls in the MySQL, Redis, MongoDB or Neo4j drivers, or
tokio: its only dependencies are serde, serde_json, serde_yaml, once_cell, rusqlite
(SQLite) and crc32fast. An embedder that used those backends depends on
`kulyrax-backends`, with the matching features, or on `kulyrax-adapter-<name>`
directly, and registers them on its runtime.

Before (0.8):

```toml
[dependencies]
kulyrax-core = "0.8"   # every driver came along
```

After (0.9 and later), every backend through `kulyrax-backends`:

```toml
[dependencies]
kulyrax-core = "0.11"
kulyrax-backends = { version = "0.11", default-features = false, features = ["mysql", "redis"] }
```

```rust
let runtime = KulyraxRuntime::load_with_backends(
    config, mappings, kulyrax_backends::register_default_backends,
)?;
```

Or one backend crate directly:

```toml
[dependencies]
kulyrax-core = "0.11"
kulyrax-adapter-mysql = "0.11"
```

```rust
runtime.register_adapter_factory("mysql", kulyrax_adapter_mysql::factory);
```

`kulyrax-backends` builds every backend by default (feature `all`). SQLite and the
file stores stay in `kulyrax-core`.

## Fixes
- **File stores: a projection could be lost after an OS crash or power loss** while
  its checkpoint survived, and a process crash mid-event could leave a data file and
  its guard out of step. See Highlights.
- **Source checkpoints are now durable** (fsync before and after the rename). Before,
  a power loss could lose or tear the checkpoint file.

---

## Known limitations
- Neo4j: an edge's endpoints are matched by node `id` across all labels, and so
  is a node's tombstone. Two node labels that share an id interfere.
- On Windows, a directory cannot be fsynced; renames rely on NTFS journaling its
  metadata in order (not verified with a power cut). Linux and macOS fsync the
  directories.
- File-store throughput is bounded by the cost of creating files: two per event
  (data and guard). On the Windows laptop used here that caps a store at about
  900 events/s, short of the 2,000 events/s goal. Antivirus real-time scanning of the
  store directory cuts it to a few hundred. Numbers from a Linux machine will follow.
- Every number in `docs/ledger/` is an internal baseline from one Windows laptop.
- Kulyrax's own bookkeeping still uses pre-rebrand names (`conduit_projection_state`,
  `.conduit/`, `__ConduitGuard`).
- Release binaries are not code-signed.
