# Kulyrax v0.9.0

## Status

Alpha. This release makes Kulyrax easy to try (prebuilt binaries, `kulyrax init`),
safer to operate (`dry-run` no longer writes, `kulyrax reload`, startup checks), and
moves every networked backend out of the engine. It contains **breaking changes**; see
[Upgrading from 0.8](#upgrading-from-08).

---

## Highlights

### Prebuilt binaries
Each tagged release now publishes `kulyrax` for Linux x86_64, macOS (Apple Silicon and
Intel) and Windows x86_64, each with a SHA-256 checksum. No Rust toolchain needed.
`kulyrax --version` reports the version.

### `kulyrax init`
`kulyrax init my-project` writes a commented starter project (config, routing, one
mapping, sample events) that runs immediately: it projects into JSON files, so no
database is needed. It refuses to overwrite existing files.

### `kulyrax reload`
`kulyrax reload --config config.yaml` makes a running `kulyrax run` (without `--once`)
or `kulyrax ingest` re-read its config, routing and mappings without restarting. The
switch happens between batches, after the new configuration has been validated and
its adapters built. An invalid change is rejected with the reason and the process
keeps running on the previous configuration. Changing `sources:` still needs a
restart.

### `dry-run` is now actually dry
In 0.8, `kulyrax dry-run` called the real write path and **wrote to the database**.
It now builds no adapter and contacts no store. It shows, for each routed adapter in
execution order, the write a live run would attempt: target, entity key, values and
write mode. It uses the same projection builders and upcasting as a live run, and
exits 1 if any write can't be resolved.

### One format for everything you write
Config, routing and mappings are all YAML. Routing moves from `routing.json` to
`routing.yaml` (see upgrading). Events stay JSON: that is the producer contract.

### Mappings: `.yml` and subfolders
Mapping files may end in `.yaml` or `.yml`, and may be grouped into subfolders of
`mappings/<kind>/`, e.g. `mappings/sql/orders/order_created.yaml`. Hidden files are
skipped. A duplicate event now names both files.

### Elasticsearch document backend
`type: elasticsearch` projects documents into Elasticsearch, with the guard stored in
the same document so every write stays atomic, and optimistic concurrency via
`if_seq_no` / `if_primary_term`.

### Producers can see dead-lettered events
gRPC `Ack` carries `dlq_events`, the number of events in the acknowledged batch that
were dead-lettered rather than projected, and `ack_protocol_version` (`>= 1` means the
server populates `dlq_events`). See `docs/producer-contract.md`.

### Every networked backend is its own crate
Postgres, MySQL, Redis, MongoDB, Neo4j and Elasticsearch live in
`crates/adapters/<name>` and are registered by `kulyrax-backends`, one Cargo feature
each. `kulyrax-core` no longer depends on any database driver or on tokio. The YAML
`type:` names are unchanged.

### Misconfigured adapters stop startup
A bad connection URL, a rejected adapter config, or an unregistered `type:` now stops
`run`, `replay` and `ingest` at startup with every failing adapter listed, instead of
failing every event routed to it. A malformed Neo4j URI is caught here too.

## Upgrading from 0.8

### Everyone
- **Routing is YAML.** Rename `routing.json` to `routing.yaml`, write each entry as
  `EventType: [adapter-id, ...]`, and update `routing: file:` in the config. A JSON
  routing file now fails at startup with these instructions.
- **Mappings in subfolders are now loaded.** If you kept non-mapping YAML (drafts,
  notes) inside `mappings/<kind>/`, move it out.
- **Adapter failures surface at startup.** A config that started before but failed
  every event for one adapter now refuses to start. Neo4j now connects at startup
  rather than on the first event.

### Embedding `kulyrax-core`
- `AdapterConfig::{MySql, Redis, MongoDb, Neo4j}` are removed. These backends resolve
  through the registry: call `kulyrax_backends::register_default_backends` on your
  `KulyraxRuntime` (or `load_with_backends`).
- `AdapterFactory` is now `Fn(&CustomAdapterConfig, &AdapterBuildContext)`. The context
  carries the mappings (`MappingSet`), upcasters and migration policy, so factories no
  longer capture them at registration time. `CustomAdapterConfig::backend_config()`
  deserializes your `config:` block.
- `KulyraxRuntime::{sql,document,kv,graph}_mappings()` are removed.
- `KulyraxRuntime::dry_run_once` now takes `(&self, &Event)` and returns
  `Result<DryRunReport, PipelineError>`. `pipeline::dry_run` no longer takes a
  backend-registration callback.
- `execute_event_with_mode` and `ExecutionMode` are removed (the `DryRun` mode wrote,
  too). Use `KulyraxRuntime::dry_run_once`.
- `pipeline::run_source_loop` takes an `on_reload` callback, and its
  `register_backends` (like `kulyrax_ingest::serve`'s) must be
  `Fn(&mut KulyraxRuntime) + Clone + 'static` instead of `FnOnce`. Plain functions such
  as `register_default_backends` already qualify.

### Contributors
- Crate directories drop the `kulyrax-` prefix (`crates/core`, `crates/adapters/postgres`).
  Package names, `-p kulyrax-*` and `use kulyrax_*` are unchanged.

## Fixes
- `dry-run` wrote to the target stores (see above).
- An embedded runtime that rebuilt its adapters after `run_sources` built them with no
  mappings, so every later event failed.
- Postgres `smallint` / `integer` columns failed to bind; values now bind at the
  column's real width.
- Validation rejected SQL and document mappings routed only to registry backends such
  as Postgres.
- The SQLite adapter opened a new connection for every event. It now keeps one
  connection in WAL mode with `synchronous = FULL`, about 3.6× faster with the same
  durability. SQLite now keeps `-wal` and `-shm` files next to the database while it
  is open, and WAL mode does not work on network filesystems.

## Known limitations
- Kulyrax's own bookkeeping still uses pre-rebrand names: the `conduit_projection_state`
  SQL table, the `.conduit/` folders of the file adapters, and the Neo4j `__ConduitGuard`
  label. Renaming them needs a data migration and is planned separately.
- Adapter paths (`sqlite.path`, `file.root`) resolve against the folder you run
  `kulyrax` from; sources and routing resolve against the config file's folder.
- Release binaries are not code-signed, so macOS and Windows warn on first run.
- Throughput is bounded by one durable commit per event per adapter. On a Windows
  laptop that is tens of events per second; committing each source batch in one
  transaction is planned.
